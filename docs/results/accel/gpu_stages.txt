Stream E: GPU image stages (GLES 3.1 compute; core/src/gpu.cpp, resample.h). Measured 2026-10-21.
Machine: i5-14400F, RTX 5060 (driver 591.44), Windows 11; host harness build-host-win (MSVC /fp:precise,
Mesa 26.2.4 mesa-dist-win: llvmpipe via GALLIUM_DRIVER=llvmpipe, the NVIDIA GPU via the default d3d12 driver).
SPEED MODE: smoke only (3 DocUNet photos with the baseline nets, 2 round-4 photos). The full gate is
`host/gpu_stage_gate.sh OUT full`, run once by the Coordinator. Timings are single runs / medians of 3-5
on a shared machine (other agents running): treat differences below ~10 ms as noise.

Stages moved (each one call, CPU fallback on any failure, byte-identical output by construction):
  stage-1 page + uv-spread pages + orientation page: remap_cubic_gpu -> Gpu::remap_dense (exact
    per-pixel map still made on the CPU; only the bicubic runs on the GPU). Default policy: OFF.
  global remap (warpmap A_img; the darkness that follows stays on the CPU): remap_offset_gpu ->
    Gpu::remap_offset (offset grid bilinear in a `precise` shader). Default policy: ON; refused on a
    context without `precise`.
  before page: already resample_any(use_gpu) (unchanged).

Reading: on this desktop the final resample (already GPU) and the global remap gain; the dense stage-1 /
orientation bicubic loses (CPU map evaluation + 2 float maps upload > the 8-thread CPU remap), hence the
policy default. Phone numbers: not measured (HUMAN GATE in the Stream E report).

the other photos skip it and "global_remap" is the darkness alone). 1_1, d3d12: global_remap+darkness
104.0 CPU vs 51.6 ms GPU (all on), 81.9 vs 59.0 ms (default policy); stage-1 page 21-35 ms CPU vs
